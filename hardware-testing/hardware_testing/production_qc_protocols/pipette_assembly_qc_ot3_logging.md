# 装配 QC 失败证据包

适用协议：`pipette_assembly_qc_ot3.py`。日志记录复用已有硬件动作和读数，不额外采样或改变测试阈值。

## 部署

在 App 中重新导入协议，并同步机器人端 `hardware_testing/drivers/data_center_client.py`，以支持失败附件按报告分目录上传。
仅支持 `.log` 的旧上传模块仍将日志上传到归档根目录；`.json` / `.encoder.csv` 保存在机器人本地，标记 `skipped_unsupported`。
已支持附件、但尚未支持子目录的旧模块仍上传到根目录。日志注释与 JSON 会说明实际目录，不会因传入旧接口不支持的参数而中止 QC。
扫码超时相关的 `helpers_ot3.py` 版本要求保持原有设置。
8 通道漏液通道录入还需要同步当前 `hardware_testing/drivers/liquid_calibration_keyboard.py`，其中新增了完整数字串输入支持。

服务器归档根目录仍为 `root@192.168.6.55:/opt/pipette_assembly_qc_log/`，每份报告使用 `<SN>_<YYYYMMDDTHHMMSSZ>/` 子目录。例如：

```text
/opt/pipette_assembly_qc_log/P1000M12345_20261029T031626Z/
    <原报告主文件名>.log
    <原报告主文件名>.json
    <原报告主文件名>.encoder.csv  （已有编码器数据时）
```

SN 优先取报告记录的被测左侧移液器序列号；时间取报告的 `test_time_utc`（UTC 创建时间），不是失败时间或上传时间。同一份报告的所有附件使用同一目录，文件名和本地保存位置不变。
扫码尚未完成时，SN 可从已记录的左侧移液器身份取得；无法取得时使用 `unknown-SN`。报告时间缺失时先使用报告运行 ID 中的时间；尚未创建报告时使用失败日志创建时间，并保留微秒。JSON 的 `archive_directory` 记录 SN 与时间来源，各附件记录实际上传目录。
SN 中不适合路径的字符会替换并附加短哈希，避免不同 SN 替换后重名。

`Operator=Unused` 时测试报告 CSV 仅保存在本地；其他操作员仍按原流程上传测试报告。失败日志独立归档，不上传测试报告 CSV。

## 原有测试报告输出

测试报告的格式、字段、文件名、保存路径、保存时机和上传规则沿用原有逻辑。运行异常时仍先尝试保存部分报告，再归档失败日志。
新增失败日志仅读取内存中的报告数据，不再次保存正式报告，不创建备用报告 CSV，也不把正式报告加入失败附件上传。

## 文件

- `.log`：失败摘要、最后异常动作、已有读数、版本、Labware Offset、测试执行状态、检查建议及完整异常栈。
- 同名 `.json`：版本化结构、公共运行 ID、所有报告行、动作记录和每个附件的保存/上传状态。
- `.encoder.csv`：如该报告目录已经生成 `encoder_debug.csv`，复制为独立命名附件。

元数据未完成时，已获取的报告行也会记录在 `.log` / `.json` 中；不存在的读数不会被补成零或 PASS。
同一次执行可产生电流速度和装配两份报告，各自保留报告 ID，使用共同的日志运行 ID。

## 右侧点水失败日志

右侧 P1000S 点水测量抛出异常时，立即在本地保存本次错误快照，此时不上传。等到左侧报告结束汇总，或协议异常退出进行统一失败归档时，再将右侧快照与左侧失败日志统一上传到同一报告的 `<左侧SN>_<UTC>/` 目录。例如 50 µL 吸头的附件为：

```text
<原报告主文件名>.right-reference-50ul.log
<原报告主文件名>.right-reference-50ul.json
```

已有编码器数据时还会附带同前缀的 `.encoder.csv`。200 µL、1000 µL 使用各自规格后缀；不同规格及最终汇总日志不会相互覆盖。目录仍使用左侧被测移液器 SN 和报告原始 UTC 时间。
快照包含右侧身份、已有点水动作与读数、异常栈，并注明该规格左侧测量未执行。最终日志的 `right_reference_failure` 事件也保留该异常及其是否被测试处理。
可处理的点水失败仍按原流程跳过本规格左侧测量、继续下一规格；原本需要中断的异常仍中断并走原运行失败归档。上传失败保留本地文件，不改变上述流程；不新增正式 CSV 保存或上传。

## 8 通道漏液通道录入

适用于 P50M、P1000M 每轮漏液测试。回答 `no` 后立即保存本轮 FAIL，移液器保持在观察漏液的位置，等待测试人员用小键盘录入漏液通道。有效通道提交并记录后，才执行原有下降、排液、吹出和退头操作。

- 输入 `138` 并按 Enter，表示通道 1、3、8；输入 `12345678` 表示全部八个通道。
- 每位数字代表一个通道，仅允许非空的 `1`～`8` 连续串，不加空格或逗号；乱序和重复通道会排序、去重，例如 `8313` 记录为 `[1, 3, 8]`。
- Backspace 删除上一位，Esc 清空当前内容，Enter 提交。空输入、0、9 或其他字符会要求重新输入，不会把 FAIL 改成 PASS。
- 等待通道录入没有总超时；暂停和取消仍可使用。小键盘断开后自动尝试重连，未提交内容需重新输入。无效输入或等待期间不执行排液、退头；取消录入时保留已记录的 FAIL，注明通道录入未完成，并中断该测试步骤。

回答 `yes`、单通道移液器、模拟运行及压力夹具测试沿用原流程，不增加通道录入。
每轮通道写入该 `droplets-<等待秒数>` 行的失败原因，并随 `.log` / `.json` 上传；正式 CSV 的行、列、判定和上传规则不变。
JSON 的 `trace.events` 中，`liquid_leak_channels` 保存原始数字串、拆分后的通道列表、轮次、等待时间、安装侧及吸头容量；`source=operator` 表示人工观察结果。
`liquid_leak_channel_input_required` 表示已发现漏液、需要补充通道；若没有对应的完成事件，则不能推断具体漏液通道。

## 读取顺序

1. 查看 `stage`、`runtime_error` 和 `trace.last_failure`。后者保留发生异常时的动作、嵌套测试上下文及当时最近读数，清理动作不覆盖原始现场。
2. 对照 `trace.identity` 的协议 SHA256、公共函数/上传模块 SHA256、软件和固件版本、实际型号与编号。
3. 检查 `trace.tests`：`passed`、`failed`、`execution_error`、`skipped_by_configuration`、`not_started`、`not_run_due_to_previous_failure` 含义不同。已被测试处理的异常另存为 `last_handled_exception`。
4. 查看 `report_rows` 和 `trace.events`。报告行带独立 `error_codes`、原始值、相对时间和失败原因；测试阈值保存在 `TEST-THRESHOLDS` / `PRESSURE-CONFIGURATIONS`。未分级的原始样本为 `unknown`，尚未写入的行为 `not_recorded`。
5. 查看 `recommendations` 中的证据、检查顺序和复测要求。`needs_confirmation` 表示待验证原因，不能当作换件结论。

## 证据边界

- `latest_readings` 是带采样时间的最近读数，不等于触发压力保护瞬间的数值。底层未提供的触发压力、方向或传感器保留未知。
- 探针安装状态来自操作员恢复运行的确认，不是额外传感器检测。
- 协议执行器中优先计算实际执行源码的 SHA256；无法取得源码时明确记录不可用，不搜索可能过期的同名文件。
- 运行中记录保存在内存，捕获失败后写入文件；断电或进程被强制终止不保证能生成证据包。
- JSON 最后上传，服务器清单对自身标记 `pending_self_upload`；这是上传前的状态。机器人本地清单和运行注释记录最终上传结果。
- 某个文件上传失败仍尝试其余文件；保存/上传异常不会替换原始 QC 异常。
