# Flex 移液器 EEPROM 身份配置协议

`provision_pipette_ot3.py` 是一次处理一支左侧移液器的维护协议。它使用连接到 Flex 的扫码枪读取条码，再启动独立 CAN worker 读取 EEPROM。可选择只读检查、直接写入、空白移液器首次烧录、清除后写入或只清除条码。只清除条码需扫描匹配的原码并暂停确认，清除后独立读回全 `FF`，不重启服务；空白身份会影响后续识别和协议启动，需重新烧录。写入模式默认不重启 robot-server；勾选“写入后重启服务”时，直接写入在 worker 写后读回成功后、先清除再写入在最终独立复查通过后，才安排整次运行成功结束时自动重启服务。原有 `hardware/opentrons_hardware/scripts/provision_pipette.py` 保持不变。

协议要求 `robotType=Flex`、`apiLevel=2.20`。目标固定为左侧（`left`），序列号由扫码录入，不提供安装侧选择或文件输入。运行参数包括操作模式 `operation`（默认 `bootstrap`）和“写入后重启服务”开关（默认关闭）：

| `operation` | 操作 | 扫码顺序 |
| --- | --- | --- |
| `inspect` | 只读检查，不修改身份或操作服务 | 左侧移液器条码一次 |
| `write` | 直接覆盖为扫码新码，允许与当前身份不同；默认不重启服务，可由开关启用 | 要写入的新条码一次，不需要原码 |
| `bootstrap`（默认） | 空白或未知身份移液器首次烧录；启动协议时左侧必须暂不连接，扫码后按暂停提示安装，再直接写入并读回 | 目标序列号一次，不需要原码 |
| `clear_then_write` | 确认后清除，再写入新条码；无需原码匹配；默认不重启服务，可由开关启用 | 要写入的新条码一次，不需要原码 |
| `clear` | 只清除条码，核对原码并确认后清除 20 字节身份，独立读回全 `FF`；不重启服务 | 当前已烧录身份对应的原条码一次 |

从旧版升级时，请重新上传新版协议并创建新运行，在新运行中选择 `operation`。不要继续使用旧版分析结果或已创建运行的参数配置。

## 适用边界

- 目标是 Flex 移液器的 20 字节身份区域，包括产品类型、版本和序列号尾码。这不是固件烧录，不会清空整片 EEPROM。
- 移液器必须已运行能响应 CAN EEPROM 请求的应用固件。协议不会自动退出 bootloader，也不会安装固件。
- 只读检查返回实际身份，即使它与扫描条码不同，也能显示当前条码和完整的 20 字节原始数据。不能解析的非空白身份会明确显示为“非空白身份”。只读成功仅表示读取成功，不代表已写入或核对原码。
- 直接写入只需扫描目标新码，**不要求新码与 EEPROM 当前身份一致**，允许覆盖不同条码，也允许替换无法解析的非空白身份。目标新码仍必须通过完整格式校验，操作员须在扫码前核对其型号、版本与实物一致；扫码后由单次 worker 事务读取当前身份、写入 20 字节新身份并读回验证，不先清为全 `FF`。与目标相同则做幂等确认。
- 只清除条码会将 20 字节身份写为全 `FF`，必须扫描匹配的原码并暂停确认，随后独立读回验证；不会写入新码或重启服务。清除后写入仍会使用实际预检快照，防止确认后目标状态发生变化；直接写入不再做协议层预读快照，以缩短耗时。
- 先清除再写入同样只扫描目标新码，不需要扫描或匹配原码，允许处理不同有效身份或无法解析的非空白身份。新码必须在清除前通过格式校验，操作员须确认新码的型号、版本及序号确实属于这支实物。
- 协议不需要 `load_instrument()`。`bootstrap` 模式专门绕过空白身份的启动阻断：创建运行时左侧必须暂不连接移液器，先让 robot-server 正常初始化并启动协议；扫码后协议暂停，操作员在机器人保持静止时安装空白移液器，继续后才启动 CAN worker。若在创建运行前就连接全 `FF` 或未知身份移液器，robot-server 仍会在协议开始前报 `InvalidPipetteName`，App 无法进入 `run()`。
- 协议不会主动移动到扫码位置，也不主动调用 `home()`，由操作员将扫码枪对准标签。但正常协议执行器可能在 `run()` 之前以及结束时归零，所以本方案不能承诺机器人完全不运动，也不能替代专用的无运动生产烧录工装。
- CAN worker 只核实 EEPROM 读回值，不负责重启。只有打开“写入后重启服务”时，`write`、`bootstrap` 和 `clear_then_write` 才安排一个独立的 systemd 临时服务，在确认整次运行成功后重启 `opentrons-robot-server.service`；不会重启整机、CAN 服务、显示应用或其他服务。默认关闭时不做 systemd 预检或服务操作；`inspect` 和 `clear` 不操作服务，即使打开重启开关也不重启。
- robot-server 服务重启不保证所有软件部署方式下的硬件身份缓存都会刷新，尤其是硬件控制运行于独立进程时。App 恢复连接后仍需核对仪器身份和校准状态，再进行新的 QC 运行。
- 本实现尚未做实机烧录、清除、自动服务重启及断电后的保持性验证。协议不会主动断电或重启整机来验证持久性，离线测试不能替代这些确认。

从仓库根目录 `/Users/yew/opentrons` 执行现有部署命令，将 `hardware-testing` wheel 推送到目标机器人：

```sh
make -C hardware-testing setup push-ot3 host=192.168.6.61
```

取消两种写入模式原码匹配限制的版本同时修改了协议与 worker，因此两者都必须更新。仅上传新协议时，旧 worker 仍可能拒绝不同身份的写入，或不认识组合模式使用的清除参数。

`drivers/provision_pipette_protocol.py` 随该 wheel 一起部署。`push-ot3` 按现有 Makefile 流程安装包并重启 `opentrons-robot-server` 服务，还会推送绘图网页、描述文件和 labware 等已有资源。这是部署时的服务操作，与协议运行结束后的条件重启分别执行。

首次烧录空白或未知身份时，使用不依赖 robot-server 的维护入口。先停止服务，避免多个 CAN 客户端同时访问；工具会手工询问生产系统分配的序列号，读出当前身份，确认后写入并读回验证：

```sh
ssh root@<robot-ip>
systemctl stop opentrons-robot-server.service
cd /opt/opentrons-robot-server
python3 -m hardware_testing.drivers.provision_pipette_manual --which left
systemctl start opentrons-robot-server.service
```

工具不需要现有条码，但必须有生产系统分配的完整目标序列号。`--serial <serial>` 可用于非交互调用；`--yes` 可跳过确认，生产现场应保留默认确认步骤。

远端安装使用 `--no-deps`，不会顺带安装或更新 `opentrons_hardware` 等依赖；worker 仍依赖机器人现有的兼容版本。推送 `hardware-testing` 不会改动原烧录脚本或 `opentrons_hardware` 包中的旧 worker。

**电脑上的文件存在不等于机器人已部署，上传协议也不会自动安装 worker。** 在机器人维护终端，使用与协议相同环境的 `python3` 执行下面的只读定位命令。它只定位新 worker 并打印文件信息，不导入或执行 worker，不访问硬件：

```sh
python3 - <<'PY'
import importlib.util
import sys
from pathlib import Path

try:
    spec = importlib.util.find_spec("hardware_testing.drivers.provision_pipette_protocol")
except (ImportError, ValueError):
    spec = None
if spec is None or not isinstance(spec.origin, str):
    raise SystemExit("当前 Python 环境找不到 hardware_testing.drivers.provision_pipette_protocol")
worker = Path(spec.origin).resolve()
print("Python:", sys.executable)
print("worker 路径:", worker)
print("worker 已存在:", worker.is_file())
PY
```

若终端的 `python3` 不属于协议使用的环境，应先进入相同环境，或使用该环境 Python 的完整路径执行上述命令；不要根据电脑上的路径推测机器人路径。

两种含清除的模式要求新模块内的 worker 支持 `--action clear`。`clear_then_write` 由协议依次调用 worker 的现有动作完成，不是新的 worker CLI 动作。组合模式的清除调用额外传入 `--allow-clear-without-original`，允许以实际身份快照确认清除，不核对扫描原码。该参数仅允许用于 `clear`；普通 `clear` 调用默认仍核对原码。

`production_qc_protocols` 被排除在 wheel 外，因此完成 `push-ot3` 后，仍需在 App **重新上传新版 `provision_pipette_ot3.py` 并创建新运行**，先选择 `operation=inspect` 检查。本文提供部署方法，并不表示已执行向机器人推送或完成实机验证。

协议默认使用 `socketcan`、`can0`。在目标机器人上确认 CAN 接口和软件版本匹配后，先执行只读检查。不要同时运行另一份 provisioning worker、原始交互烧录脚本或其他 EEPROM 写入程序。

仅当选择 `write` 或 `clear_then_write` 并打开“写入后重启服务”时，运行开始才会检查 `systemd-run` 和 `systemctl` 是否存在、robot-server 服务是否为 `loaded` / `active`，以及本机接口能否确认当前运行处于 `running`。该检查只读，不创建重启任务，也不证明稍后提交任务或执行重启的权限一定可用；检查失败则在清除或写入前停止。真正的重启任务只会在最终写入和读回核对通过后提交。

## 准备扫码枪和实物标签

将一支受支持的扫码枪连接到 **Flex 的 USB 接口**，并在运行前确认机器人已将它识别为扫码枪外设。本协议复用机器人已有的 `RTScanner` / `SmartScanner` 串口驱动与连接，不会自行搜索串口或创建第二个驱动连接。没有已识别的扫码枪、识别到多支扫码枪或硬件代理接口不受支持时，会停止运行。

扫码枪接在电脑上，或者配置成 HID 键盘模拟输入，都不属于当前支持的输入方式。普通 USB 键盘输入不能代替机器人扫码外设；具体设备是否可用，以目标机器人软件能否通过上述驱动识别并读取为准。

- 两种写入模式均只扫描准备赋予**左侧**移液器的新条码。不要扫描包装、另一支移液器或扫码枪自身的标签。
- 支持已知型号前缀 `P1KS`、`P1KM`、`P1KP`、`P50S`、`P50M`、`P1KH`、`P50H`、`P2HH`，随后为大写 `V`、两位版本数字和 1–12 位 ASCII 字母或数字尾码。协议去掉扫码文本两端的空格、制表符及换行后，严格验证整个序列号；空尾码、下划线、中文及其他符号均不接受。
- 每次扫码阶段遇到空读或格式错误会继续尝试，重试窗口为 10 分钟。该阶段接受第一个格式有效的序列号；格式有效不能证明标签属于左侧实物，修改前必须人工核对，扫错有效条码应取消并重新运行。
- 扫码期间，App 运行日志中的当前步骤会提示需要扫描的条码，每次重试都会再次显示。两种写入模式提示扫描目标新码，`clear_then_write` 明确提示“无需扫描原码”。空读和格式错误会提示继续扫码。与 96 通道 QC 协议相同，使用运行提示，不增加扫码暂停弹窗；扫码成功后自动继续。`write` 会直接进入写入，`clear_then_write` 保留写入前的人工确认。
- `clear_then_write` 只扫描新码一次；新码不要求与旧码相同，但必须与实物型号相符。在新码读取、格式验证和人工确认完成前不会清除身份。
- 协议不移动移液器或扫码枪，请操作员对准可见的实物标签。一次运行只处理一支；处理下一支时结束当前维护运行，按现场流程安装，再创建新运行并重新扫码。

10 分钟期限在每次驱动读取前后检查，不会强行中断进行中的串口读取。单次读取和 App 暂停、取消的响应可能有延迟，具体取决于机器人上的驱动及通信状态；不能将其视为精确到时即退出的硬超时。

## 先做只读预检

1. 完成 worker 部署，将协议上传到 App。
2. 确认一支扫码枪已连接并被机器人识别。需要只读检查时，显式选择 `operation=inspect`；默认的 `operation=bootstrap` 要求启动时左侧暂不连接移液器，扫码后按暂停提示安装，再继续写入并读回验证。
3. 启动运行，按提示扫描左侧移液器实物标签，查看协议显示的左侧目标序列号和当前 EEPROM 身份。
4. 查看当前身份、扫描条码和 20 字节原始数据。需要赋予目标新码时可选择“直接写入”或“清除后写入”，两者均无需扫描匹配当前身份的原码；当前为空白、不同有效身份或无法解析的非空白数据时均可进入写入流程。读取超时、目标条码格式不支持或硬件初始化失败需先解决。

只读预检不发送身份写入命令，也不安排服务重启；正常协议执行器仍可能执行归零。模拟或协议分析会跳过扫码、worker 和服务重启，不会连接 CAN，不能作为实物预检通过的证据。

也可以在机器人维护终端，使用与协议相同 Python 环境直接运行只读检查，避免依赖协议能否开始执行：

```sh
python3 -m hardware_testing.drivers.provision_pipette_protocol \
  --action inspect \
  --which left \
  --serial P1KSV3120211129A08
```

执行前必须把示例序列号替换为左侧实物标签的真实值，保留 `--which left`。该命令只读取 EEPROM，不使用扫码枪；它仍要求应用固件和 CAN 通信正常。

worker 向 stdout 返回单行结构化 JSON，并以退出状态区分成功和失败。协议在内存中核对返回的 action、安装侧、目标值和读回值；不能只凭提示中出现“成功”字样判定结果。直接运行 worker 不会触发服务重启。

只读检查成功时，退出码为 `0`，JSON 中 `schema_version=1`、`action="inspect"`、`success=true`、`status="ready"`、`write_attempted=false`、`changed=false`。`before.raw_hex` 是 40 位十六进制身份数据，`before.blank` 表示是否为空白。`ready` 表示本次读取完成，不表示当前身份与 `requested_serial` 一致；写入和清除都会检查实际身份快照。检查失败时退出码非零，查看 `error` 字段。不要手工拼接这样的 JSON 来代替实际检查。

worker 还支持 `--timeout`、`--attempts` 和原有 CAN 连接参数。协议固定使用每次通信超时 `1.0` 秒、最多 `3` 次写后读回，以及子进程轮询期间 `30` 秒的外层期限。如果操作员手动暂停协议，外层期限检查会延后到协议恢复或取消；worker 自身的 CAN 通信超时继续生效。重试针对读回，不会循环重复发送身份写入。worker 不保存结果文件，旧的 `--log-file` 参数已移除，使用时会报参数错误。

## 直接写入

1. 用左侧实际标签完成上述只读预检。
2. 创建新运行，选择 `operation=write`，按提示扫描要写入左侧移液器的真实条码。
3. 如果打开“写入后重启服务”，协议先通过自动重启能力预检；关闭时跳过该预检。之后扫描标签。无需原码一致，也不会弹出人工确认；扫码完成后由单次 worker 事务读取当前身份、覆盖 20 字节身份并读回验证。
4. 直接写入是快速路径，操作员必须在扫码前核对左侧实物型号、版本及待写入的新条码。发现扫错标签时应立即停止运行，不要等待或继续；写入阶段不要更换或断开移液器，也不要修改 EEPROM。
5. worker 在同一次写入调用中读取当前身份、发送写入并完成写后读回验证；直接写入不再启动额外的预检 worker，因此省去一次进程启动和重复 CAN 查询。
6. 该快速路径要求运行期间没有其他 EEPROM 写入程序并发操作目标；如果需要协议层预检快照和人工确认，应先选择 `inspect`，再另行执行写入流程。`clear_then_write` 仍保留写入前快照和写入后的独立只读检查。
7. 如果启用了重启开关，验证通过后协议提交等待运行结束的重启任务，并显示安排结果；否则直接结束本次写入流程。
8. 不重启时，App 可能继续缓存旧身份；开始新的 QC 前按现场流程刷新服务或重新建立硬件连接。启用重启时，App 恢复连接后仍需核对移液器身份与校准状态；提交成功只表示已安排任务，不能据此认定服务已重启。

`--action write` 可以省略 `--expected-before-hex`，此时 worker 会在同一次事务中读取当前身份后直接写入并读回验证。需要把写入绑定到已有预检快照时，仍应提供实际读取到的完整 40 位值；不要手工猜测或固定为全 `FF`。`--action clear` 仍要求显式提供该参数。

如果当前身份已与目标完全相同，该次运行可以完成幂等确认，不重复发送写入；这不能证明此前由谁或何时完成了首次写入。当前身份与目标不同则直接写入新身份，不经过中间空白状态。若需要显式执行“清除为全 FF 再写入”，可选择下面的先清除再写入模式。

## 空白移液器首次烧录（App 协议）

1. 确认左侧空白移液器已经取下，保持左侧安装位为空；扫码枪仍连接在 Flex 上。
2. 在 App 创建运行，选择 `operation=bootstrap`。如果空白移液器已经连接，robot-server 会在协议启动前报 `InvalidPipetteName`，必须先取消运行并取下移液器。
3. 启动协议，按提示扫描生产系统分配的目标序列号。这个条码是目标身份输入，不要求来自移液器当前 EEPROM；如果实物没有标签，应使用生产系统提供的目标条码或临时打印的目标条码。
4. 扫码成功后协议会暂停。确认机器人保持静止，在暂停期间安装需要首次烧录的空白移液器，确认连接牢固后点击继续。
5. 协议使用单次 worker 事务读取当前身份、写入目标 20 字节身份并读回验证。全 `FF`、全 `00` 或其他未知身份都可以被覆盖，不需要原码。
6. 写入读回成功后，请求工具检测并等待机器人识别目标条码，再显示识别结果。默认不重启服务；若打开“写入后重启服务”，最终运行成功后才安排 robot-server 重启。

该模式不修改 robot-server，也不要求移液器在协议启动时存在；它利用协议启动前左侧为空的窗口，避开未知身份初始化失败。不要在协议暂停前安装空白移液器，也不要在 worker 写入期间拔插移液器。

### 已读回成功但结束时报 `InvalidPipetteName 65535`

2026-11-23 的运行日志 `APRQC2_provision_pipette_ot3_2026-11-23T06_23_33.866Z.json` 显示：14:24:14（北京时间）已经读回验证目标 `P50SV3520240111A02`，14:24:18 才在结束清理时出现 `Invalid pipette name key 65535 on mount LEFT`，所有协议命令均已成功。因此，这次故障发生在写入验证之后，不能据此认定 EEPROM 写入失败。

空白移液器安装时，后台检测可能先缓存型号 `0xFFFF`（65535）；独立 CAN worker 随后写入并验证了有效身份，但不会更新 robot-server 的工具缓存。协议结束时硬件 `stop()` → `reset()` → `cache_instruments()` 使用这份旧缓存，仍会报未知型号。这与日志中的先成功验证、后结束失败相吻合。

修复仅修改协议与 `hardware_testing.drivers.provision_pipette_protocol`，不修改机器人 API：`bootstrap` 在单次写入和读回成功后，要求 worker 发送 `AttachedToolsRequest` 给 head，触发 robot-server 已有的工具检测流程。协议随后调用现有的 `cache_instruments()`，最多等待 30 秒，直到左侧缓存的 `pipette_id` 与目标条码一致后才结束。缓存仍为全 FF 时继续等待；缓存为空或仍是旧条码时也不能判为识别成功。

此过程不重复发送 EEPROM 写入，不重启服务。若身份识别超时，明确提示“EEPROM 已写入并读回验证，但机器人未识别新身份”，不会将缓存错误当成需要重新写入。实际仍为未知身份、检测或配置失败时，不会跳过检查或伪造成功。

**需要同时更新 hardware-testing 驱动和上传新版协议，不需要更新机器人 API。** 从仓库根目录执行（替换机器人 IP；部署过程可能重启服务，请在没有运行中的协议时部署）：

```bash
make -C hardware-testing setup push-ot3 host=<机器人IP>
```

随后在 App 重新上传 `provision_pipette_ot3.py` 并创建新的 `bootstrap` 运行。旧驱动不支持 `--refresh-tools-after-write` 时，新协议会提示重新部署。该修复已覆盖写后检测请求、检测前失败、旧空白缓存、目标条码匹配和识别超时等离线回归，仍需实机验证。已有失败运行如已出现“EEPROM 序列号核对通过”，应先只读检查实际身份，避免将运行失败直接当成未写入。

## 先清除再写入

1. 创建新运行，选择 `operation=clear_then_write`。准备要写入左侧移液器的新条码，无需原条码。
2. 协议先完成自动重启能力预检，再提示扫描新条码并校验格式，然后调用只读 `inspect` 获取当前完整的 20 字节身份。已有身份不必与新码一致，也不要求能够解析为旧条码。
3. 协议显示实际当前身份及目标新码。此时尚未清除或写入任何身份数据，也没有第二次扫码。
4. 协议暂停，展示固定的左侧目标、当前身份和新条码。操作员核对新码的型号、版本和序号与实物一致，确认后恢复。发现目标条码错误应取消并重新运行。
5. worker 使用目标新码、暂停前的身份快照及 `--allow-clear-without-original` 执行 `clear`。清除前仍要求实际身份与快照完全相同，但不核对旧条码。随后协议独立 `inspect`，必须确认完整的 20 字节为全 `FF`。
6. 协议使用**独立复查实际读取到的全 `FF` 快照**和已扫描的新条码执行 `write`，随后再独立 `inspect`，确认全部 20 字节与新身份完全一致。
7. 最终核对通过后，只有启用“写入后重启服务”时才安排服务重启；仍须等本次完整运行成功结束及正常运行历史保存完成，辅助进程才尝试重启 robot-server。

清除和写入之间不会再次扫码或安排人工确认暂停；服务是否在最终验证后重启由“写入后重启服务”开关决定。新码扫码和人工核对都在清除前完成。恢复确认暂停后不要更换、断开移液器或让其他程序修改 EEPROM。

如果清除后、写入前取消或失败，移液器可能停在空白身份；若已发送新身份写入，也可能已写入新码。流程没有自动回滚，未确认最终写入成功就不会安排重启；整次运行失败或取消也不会触发等待中的重启任务。不要直接再次烧录，应先执行只读检查，按下述维护恢复流程确认实际状态。

## 只清除条码（App 协议）

1. 创建新运行，选择“只清除条码”（`operation=clear`），左侧连接待清除的移液器。
2. 扫描当前已烧录身份对应的原条码。协议读取身份并核对；非空身份与原码不匹配时拒绝清除。
3. 协议暂停，显示左侧目标、当前身份及清除说明。核对后点击继续，将 20 字节身份写为全 `FF`，再独立读回验证。
4. 此模式不写入新码、不重启服务，即使打开“写入后重启服务”也不重启。App 可能仍显示缓存的旧条码，应以读回结果为准。
5. 后续需要恢复有效身份时，可先取下空白移液器，再选择 `bootstrap`，按先扫码、暂停后安装的流程重新烧录；若机器人无法初始化，则使用下述维护终端恢复流程。需要在同一次运行中清除并写入新码时，选择 `clear_then_write`。

**这是恢复身份区为空白，不是把整片 EEPROM 恢复出厂。** 修改范围包括产品类型（2 字节）、版本（2 字节）和序列号尾码（16 字节）。不发送通用 EEPROM 文件系统清除命令，也不清除物理标签。工程里的 `reset_eeprom.py` 从地址 28 开始清除通用数据区并重启设备固件，不是本功能，应避免将它用于清条码。

清除后 App 可能仍显示缓存的旧条码，应以 CAN 独立读回为准。重新检测全 `FF` 的产品类型时，软件会将其视为未知移液器；若发生在结束清理、归零或后续启动阶段，协议可能失败，甚至不能再从 App 启动烧录协议。这个边界同样适用于先清除再写入在中途失败后留下空白身份的情况。**不重启服务只能避免主动触发一次重新初始化，不能保证后续运行一定可启动。** 此时可取下空白移液器后使用 `bootstrap` 重新烧录；若无法启动协议，则通过机器人维护终端运行独立 worker 恢复有效身份。

终端恢复可直接使用 `provision_pipette_manual`：它会以目标新码执行只读预检，获取当前 `before.raw_hex`，确认后再执行带快照的 `write`。该入口允许覆盖全 `FF`、全 `00` 或其他未知身份，但目标新码必须符合实物型号和版本。必须在协议停止、没有其他 EEPROM 写入程序操作目标时执行；建议先停止 robot-server，避免多个 CAN 客户端同时访问。独立 worker 不需要 robot-server 硬件初始化成功，但仍要求移液器应用固件及 CAN 通信正常。

直接调用 `--action clear` 默认仍须提供匹配的原条码和实际预检得到的 `--expected-before-hex`；非空原身份不同或快照改变时拒绝清除。组合模式使用 `--allow-clear-without-original` 跳过原码核对，但该参数不会跳过快照检查，也不会自行执行后续写入；清除后写入的完整流程由协议编排。该动作不会读取扫码枪，也不会安排服务重启。

## 自动服务重启

以下只适用于 `operation=write` 和 `operation=clear_then_write` 且启用了“写入后重启服务”的运行；两者都要求最终写入及读回核对通过。重启由 `systemd-run` 启动的独立临时服务处理，等待窗口为 **180 秒**，该临时服务另设 `RuntimeMaxSec=240` 的运行上限。它先确认同一运行的 `status` 为 `succeeded`，这包含协议执行器的结束归零流程；再确认 robot-server 的正常运行历史中，已保存本协议末尾“已安排服务重启……”这条成功执行的提示。这样不会仅凭引擎已完成就提前重启，导致运行历史尚未来得及保存。

满足上述条件后，辅助进程还会再次检查当前运行没有切换，并确认没有维护运行，才执行 `systemctl --no-ask-password --no-block restart opentrons-robot-server.service`。协议不调用 `/server/restart`，也不请求整机重启。

暂停、开门阻塞或等待恢复时，辅助进程会在同一个 180 秒窗口内继续等待，不会重新计时。如果运行被取消、失败或停止，发现当前运行已切换，或者重启前发现新的维护运行，就放弃重启。本机运行状态读取出错、超时，或在等待窗口内未确认成功及历史已保存，也不会触发重启。写入前的只读能力预检通过，不能保证稍后的任务提交或实际服务重启一定成功。

如果提交重启任务失败，协议会明确报告 EEPROM 已通过读回验证，但自动重启安排失败。此时不能称为“已重启”，也不能为重试重启而盲目再次烧录；应先核对实际身份和运行状态，再按现场维护流程处理服务。

## 状态提示和常见结果

协议和 worker 不保存烧录 JSONL、结果文件或扫码记录。状态通过协议提示和 worker 的内存 JSON 结果传递；系统和 App 自身的常规日志机制保持不变。没有独立的烧录报告文件可供事后读取。

| 结果或错误 | 含义与处理 |
| --- | --- |
| 当前身份全 `FF` 或全 `00` | 身份区满足空白条件；仍需核对实物和目标序列号 |
| 当前身份已等于目标 | 可进行幂等确认，不需要更换成其他身份 |
| 清除已独立读回全 `FF` | `clear` 只完成身份清除；`clear_then_write` 会继续写入已扫描的新码 |
| 新旧条码不同 | `write` 和 `clear_then_write` 均只扫描新码，不核对原码。新码型号和版本须与实物一致 |
| 新码尚未通过校验 | 尚未清除或写入；继续按提示扫码，或取消运行 |
| 清除后写入失败或被取消 | 可能已空白或已写入新码；不自动回滚、不重启，先独立只读核对再处理 |
| 没有扫码枪或检测到多支扫码枪 | 停止；在 Flex 上只保留一支已被机器人识别的受支持扫码枪，再重新运行 |
| 扫码内容为空或格式错误 | 10 分钟重试窗口内继续扫码；对准左侧实物标签 |
| 扫码超时、设备异常或接口不受支持 | 尚未修改 EEPROM 身份；检查机器人扫码外设连接与软件兼容性 |
| 当前身份存在且与扫描码不同 | 只读检查正常显示实际身份；两种写入模式均可替换 |
| 当前身份非空白但无法解析为有效条码 | 显示实际 20 字节原始数据；两种写入模式均可替换为合法目标新码 |
| 只读或直接写入仍返回 `Existing identity is nonblank...` | 机器人仍使用旧版 worker；重新部署 `hardware-testing`，并上传新版协议、创建新运行。新版协议会在错误中补充 worker 返回的当前身份与原始数据 |
| 清除或快照绑定写入前身份与预检值不一致 | 目标状态已改变；停止本次操作，重新独立预检 |
| EEPROM 读取超时 | 无法证明目标当前状态；检查接口、左侧目标及应用固件是否正常响应 |
| worker 缺失或依赖导入失败 | 检查机器人当前协议 Python 环境中的 `hardware_testing.drivers.provision_pipette_protocol` 及现有依赖；仅重新上传协议不会安装 worker |
| worker 返回非法 JSON、非零退出码或结果字段不匹配 | 协议失败；根据页面错误重新只读核对，不能视为成功 |
| 写入后读回不一致或超时 | 未确认本次最终状态；只读复查后再决定后续处理 |
| 自动重启能力预检失败 | 仅在打开重启开关时会出现；尚未写入，检查 systemd 命令、服务的 `loaded` / `active` 状态，以及当前 `running` 运行是否可读 |
| EEPROM 已验证，但重启任务提交失败 | EEPROM 写入结果与重启失败分别处理；不代表服务已重启 |
| 重启任务已安排 | 最多等待 180 秒确认同一运行 `succeeded` 且末尾成功提示已存入正常运行历史，再检查没有新运行后尝试重启；不等于重启已完成 |
| `HardwareFailedToInitialize` 阻断协议启动 | 尚未进入 `run()`，协议内启动子进程无效；仅 App 中未识别移液器不等于发生了这一阻断 |

## 取消和中断

扫码阶段以及写入前暂停确认时取消，协议尚未发出身份写入命令；`write` 在扫码和预检完成后立即进入写入，`clear_then_write` 仍须先完成确认。扫码读取期间的取消可能等到当前驱动调用返回后才被处理；协议在接受扫码结果、进入下一阶段前再次检查运行状态。写入已经启动后，取消运行、子进程超时、网络断开或协议最终报错，都不代表 EEPROM 已回滚。遇到这些情况，应重新执行只读检查，确认实际为原身份、空白还是新身份后再继续，不能盲目重写。

写入阶段已经启动的子进程不会因为 App 的一般“暂停”操作自动回滚或暂停 EEPROM 操作。`clear_then_write` 的确认页面只是开始写入前的人工检查点；不要把写入后的暂停当作阻止写入的手段。

同样，EEPROM 已验证成功后，如果协议结束归零失败，App 的整次运行状态可能是失败，等待中的重启任务也会放弃重启。需要分别核对“身份读回已确认”“整次维护协议成功”和“服务已重启”，不能用其中一项代替其他结果。
