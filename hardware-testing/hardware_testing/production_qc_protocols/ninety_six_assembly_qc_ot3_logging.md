# 96 通道装配 QC 失败证据包

适用协议：`ninety_six_assembly_qc_ot3.py`，支持 P200 / P1000 96 通道。
沿用 `pipette_assembly_qc_ot3.py` 的失败附件格式和上传接口，记录 96 通道自身的测试项目、读数及判定标准。

## 人工确认等待

钳口灯状态和液滴保持结果的 Yes/No 确认不设总等待时限，超过 10 分钟仍等待操作员明确回答。Enter / Y 表示 Yes，Esc / N 表示 No，也可扫描 Yes / No；不会因为无人回答而自动通过或记为失败。暂停、停止和过期按键过滤保持有效。该设置仅针对本协议的人工 Yes/No 确认，不改变测试动作、判定阈值、扫码编号等待或数据上传超时。

## 自动判定失败后的确认

编号校验，以及 PLUNGER、CAPACITANCE、PRESSURE、ENVIRONMENT-SENSOR、TIP-SENSOR、ENCODER 各大项正常返回并完成原有清理动作后，检查该项已记录的 FAIL。PASS、未测试和未判定行不会触发失败确认；JAWS、DROPLETS 保留原有人工判定流程。

有 FAIL 时先保存当前 CSV，在运行记录中显示失败项目、原始数据、已有失败原因、对应型号的判定标准和本项已捕获异常，再沿用钳口灯、液滴保持等人工判断所用的 `helpers_ot3.get_user_answer()` 提示是否继续。直接使用原有 ProtocolContext 和键盘/扫码处理，不新增 App 弹窗，不修改 App、API 或键盘驱动。原始数据为 null 时表示缺失或非有限值，不能当作 0；没有记录的传感器读数不会补造。

按机器人 USB 键盘 Enter / Y（或扫描 Yes）继续后续流程，按 Esc / N（或扫描 No）停止；不需要先点击 App 的“确认并继续”。此确认没有等待超时，等待期间不执行后续测试动作，决定会写入失败证据。继续不会将原 FAIL 改为 PASS；后续完整运行仍按原顺序处理正式 CSV 和失败附件。选择停止则保留部分报告并执行原中断归档流程，未完成报告不会作为完整正式报告上传。运动、通信、清理等原本会抛出的运行异常仍直接停止，不转成可忽略的确认。

重新导入本协议即可使用该确认流程，无需配套更新 App。失败详情保留在运行记录中，键盘重连、无效回答、旧按键过滤，以及 App 主动暂停、停止和门联锁均沿用原有控制流程。

## 生成与上传

正式测试 CSV：实机完成所选测试并保存报告后，选择具名 Operator 时自动调用 Data Center 上传，不论测试结果 PASS 或 FAIL。`Operator=Unused` 跳过正式 CSV 上传。模拟分析不上传；运行异常中断时，部分 CSV 留在本地，并继续生成和上传失败附件。

正式 CSV 使用 `data_center_client.upload_data_to_google_drive(..., direct_upload=True)`，默认服务为 `http://192.168.6.55:8090`。直接发送本次 CSV，不通过服务器拉取整个机器人报告目录，也不打包源目录。客户端先创建上传记录，再提交文件并查询记录确认最终状态；仅排队不算上传成功。提交后默认最多轮询等待 900 秒，期间协议尚未结束。

如果创建记录接口 `/api/upload-records/start` 明确返回 HTTP 404 或 405，则兼容旧服务器，直接调用 `/api/upload-data/manual`，不提交 `record_id`。旧接口只有明确返回同步成功才确认为上传成功；排队或等待状态仍标记为未确认。连接超时及其他 HTTP 错误不触发此降级，避免重复提交。运行注释和失败证据中记录上传阶段、HTTP 状态、记录 ID（如有）及最终结果；本地报告保留，原 QC 判定不变。需同时更新机器人上的上传模块。

完整测试运行的顺序为：保存正式 CSV → 等待正式 CSV 上传尝试结束（成功、失败或超时）→ 有 QC 失败时上传失败附件。失败日志不会先占用上传时间。`Operator=Unused` 时跳过正式 CSV 上传，仍上传失败附件；运行异常中断、没有完整报告时直接保留部分 CSV 并归档失败证据。服务端仍在排队的超时请求无法保证其后台任务已结束，但客户端不并发提交这些附件。

实时运行出现明确的 FAIL，或启动、扫码、测试等阶段抛出异常时，生成失败证据包并尝试上传。
测试通过和模拟分析不上传失败附件。选择 `Operator=Unused` 仍会上传失败附件。

服务器位置：

```text
root@192.168.6.55:/opt/pipette_assembly_qc_log/<SN>_<YYYYMMDDTHHMMSSZ>/
    <原报告主文件名>.log
    <原报告主文件名>.json
    <原报告主文件名>.encoder.csv  （已有 encoder_debug.csv 时）
```

SN 优先使用报告中的被测移液器编号，其次使用已缓存的左侧移液器编号；均不可用时为 `unknown-SN`。
UTC 时间取报告的 `test_time_utc`，其次取报告运行 ID；尚未创建报告时使用证据包创建时间并记录来源。
文件在机器人本地与原报告保存在同一目录；报告命名尚未完成时使用带 UTC 时间的 startup 文件名。

需要将当前工程的 `hardware_testing/drivers/data_center_client.py` 同步到机器人，才能使用全部附件和 SN＋UTC 子目录上传。
旧上传模块会兼容降级：仅支持 `.log` 时，其余附件保留本地；不支持子目录时上传到归档根目录。实际状态和目录记录在 JSON 及运行注释中。
单个附件上传失败后继续尝试其余附件，本地文件保留。

## 证据内容

- `.log`：失败项目、原始异常栈、测试阶段、最近动作和读数、协议及依赖版本、Labware Offset、原判定标准、检查和复测建议。
- `.json`：`schema_version=1`，包括所有报告行、独立证据编号、动作历史、测试执行状态、原阈值、运行 ID，以及附件保存和上传状态。
- `.encoder.csv`：复制本次报告目录中已有的编码器调试数据，不额外执行编码器测试。

`trace.tests` 区分通过、失败、执行异常、配置跳过和受前序异常阻断的项目；尚未写入的报告行标记为 `not_recorded`，不会补为 PASS。
测试捕获后正常继续的异常保存在 `last_handled_exception`；导致协议停止的动作保存在 `trace.last_failure`。
已有清理动作若再次报错，会单独记录，保留原始测试异常。

最近采样读数不等于压力保护触发瞬间的读数；底层没有提供的触发值标记未知。
检查与复测建议标记为 `needs_confirmation`，供品质部门确认原因，不作为已确定的换件结论。

## 与原测试、CSV 的关系

原取头位置、动作顺序、运动参数、传感器读取次数、判定阈值和正式 CSV 的格式、命名及保存规则保持原样；新增正式 CSV 自动上传遵循上述 Operator 条件。
记录复用原动作和读数，不额外查询硬件。运行异常时沿用原逻辑尝试保存部分 CSV；失败归档不额外保存或上传正式 CSV。

JSON 最后上传，服务器副本对自身记录 `pending_self_upload`；机器人本地 JSON 和运行注释记录最终上传结果。
运行证据先保存在内存，捕获失败后写出；断电或进程被强制终止时不保证生成证据包。
